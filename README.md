# SnapSip

Aplicación web sencilla del proyecto **SnapSip** (CIN 324 — Ingeniería de Requisitos), generada historia por historia a partir de la documentación del repositorio.

## Estado actual
- **HU-01 — Autenticación de usuarios** implementada (cambio OpenSpec archivado: `hu-01-autenticacion-usuarios`).
- **HU-02 — Crear proyecto** implementada (cambio OpenSpec archivado: `hu-02-crear-proyecto`; ajuste OBS-1 `ajuste-hu-02-partes-al-crear`). Ahora se capturan las cinco cantidades de las partes de la casa y se crean las partes con cantidad prevista, sin piezas.
- **HU-03 — Inyectar piezas desde plano/archivo** implementada (cambio OpenSpec archivado: `hu-03-inyectar-piezas`). Ajuste de formato de códigos completado: `ajuste-hu-03-codigos-pieza` (`.cin324/validaciones/VAL-HU-03-2.md`). Con OBS-1 (`ajuste-hu-02-partes-al-crear`) la inyección usa las partes creadas en HU-02, crea las cantidades exactas en una sola carga, oculta el botón y rechaza reintentos. El plano/archivo se **simula en la demo** con un botón (indicación del profesor de 2026-11-18, registrada como supuesto en `.cin324/proyecto.md`): no se carga ningún archivo real. **CA2** (formato inválido / filas incompletas) no se representa, igual que CA2 de HU-01; ver `.cin324/validaciones/VAL-HU-03-1.md`.
- **HU-04 — Crear torre** implementada (cambio OpenSpec archivado: `hu-04-crear-torre`), solo para *Operario de Bodega*. Crea la tabla `torres` (migración 004) y registra cada torre con número correlativo **dentro del proyecto**, código `TOR-<codigo del proyecto>-<numero>`, estado **"Abierta"** y sin piezas asignadas. CA3 y CA4 de HU-04 (rechazo de piezas por otra parte o torre Cerrada) se implementan en HU-05; la «capacidad física» no se mide.
- **HU-05 — Asignar pieza a torre con evidencia** implementada (cambio OpenSpec archivado: `hu-05-asignar-pieza-con-evidencia`), solo para *Operario de Bodega*. Migración 005: `piezas.torre_id` y tabla `evidencias`. Asigna una pieza «Pendiente» a una torre «Abierta» del mismo proyecto y parte con una de **3 fotos de demostración** (obligatoria, ninguna preseleccionada); la pieza pasa a «Listo» y la evidencia guarda `responsable`, `fechaHoraCaptura` y `vigente` (sin columnas de usuario/fecha en `piezas`). Rechazos literales del DSS-01, incluidos HU-04 CA3/CA4. Reasignación de piezas «Listo» en dos pasos (confirmación + nueva evidencia; la anterior queda como historial no vigente); la invalidación de guías queda para HU-08. CA6: consulta de las piezas de una torre con código y estado.
- **HU-06 — Consultar piezas pendientes** implementada (cambio OpenSpec archivado: `hu-06-consultar-piezas-pendientes`; ajustes archivados: `ajuste-hu-06-selectores-proyecto-partes` y `ajuste-hu-06-selector-partes-automatico`), solo para *Operario de Bodega*. Filtra por `Pieza.estado = "Pendiente"`; no crea tablas ni columnas (la columna `torre_id` y la tabla `torres` las agregan HU-04 y HU-05). El selector de Proyecto identifica cada proyecto por cliente y código; al elegirlo, el selector de Parte se llena **automáticamente** con las partes de ese proyecto que tienen piezas cargadas, sin pulsar «Consultar». Los proyectos «Pendiente de aprobación» o «Rechazado» muestran un aviso por ausencia de piezas.
- **HU-12 — Aprobar o rechazar proyecto** implementada (cambio OpenSpec: `hu-12-aprobar-o-rechazar-proyecto`), solo para *Supervisor de Proyectos* en `/aprobaciones`. El proyecto recién creado nace «Pendiente de aprobación»; el Supervisor lo lleva a «Aprobado» o «Rechazado» sin crear campos adicionales. La inyección de HU-03 exige «Aprobado».
- Acceso mediante **selector de rol de demostración** (*Operario de Bodega* / *Encargado de Despacho* / *Supervisor de Proyectos*), **sin autenticación real** ni credenciales (regla del taller). El **Servicio de autenticación** documentado (CU-01/DSS-03) se considera **simulado/omitido** en el flujo principal de esta demo (adaptador declarado en `src/integraciones/`).
- Base de datos: **SQLite** (`data/app.db` por defecto), migraciones SQL numeradas en `src/db/migrations/` (registro en `schema_migrations`). La migración 006 agrega `partes_casa.cantidad_prevista` de forma **aditiva**: conserva los datos existentes, completa el valor con el número de piezas ya registradas por parte y no borra ni reinicia la base. La migración 007 cambia el `DEFAULT` de `proyectos.estado` a **«Pendiente de aprobación»** y convierte solo las filas históricas en «Sin piezas cargadas»: sin piezas → «Pendiente de aprobación», con piezas → «En preparación»; conserva todas las filas y relaciones, sin borrar ni reiniciar la base. `conexion.ts` desactiva `foreign_keys` mientras reconstruye la tabla y valida `PRAGMA foreign_key_check` antes de confirmar.

## Requisitos
- **Node.js 22.13 o superior** (recomendado: 22 LTS o 24 LTS). La base de datos usa el módulo integrado `node:sqlite`, que no existe en Node 20, y Vitest 5 exige Node `^22.12 || ^24 || >=26`. Comprueba tu versión con `node --version`.
- npm (incluido con Node.js). No hace falta instalar SQLite aparte.

> Al iniciar verás el aviso `ExperimentalWarning: SQLite is an experimental feature`: es normal en Node 22/24 y no afecta al funcionamiento.

## Instalación
```bash
npm install
```


## Ejecutar la aplicación
```bash
npm run dev
```
Luego abre: **http://localhost:3000**

- Selecciona o cambia el **rol de demostración** en la pantalla principal: *Operario de Bodega*, *Encargado de Despacho* o *Supervisor de Proyectos*.
- **HU-12 (Aprobar o rechazar proyecto, CU-12, solo *Supervisor de Proyectos*):** `/aprobaciones` lista los proyectos por cliente, código y estado. Los botones «Aprobar» y «Rechazar» aparecen solo en «Pendiente de aprobación»; al decidir se muestra el resultado y el estado actual. Fuera de ese estado (o si el proyecto no existe) la operación se rechaza sin modificar datos. No hay campo ni bandera de aprobación: el propio estado la implica. `/proyectos` sigue siendo exclusivo del *Encargado de Despacho*.
- **HU-01 (CA3, ejemplo protegido):** `/operaciones/despacho/ejemplo` (solo *Encargado de Despacho*).
- **HU-02 (Crear proyecto, CU-02, solo *Encargado de Despacho*):** `/proyectos/nuevo` (formulario) y `/proyectos` (listado de proyectos registrados). El proyecto se registra con `cliente`, `codigo`, `metraje` y las cantidades previstas de **Piso, Muros exteriores, Muros interiores, Entrepiso y Techo** (enteros no negativos, total entre 1 y 100). Solo se crean las partes con cantidad positiva, con su cantidad guardada; el proyecto queda en **"Pendiente de aprobación"** y con **cero piezas**; el Supervisor de Proyectos debe aprobarlo antes de inyectar piezas. Las cantidades inválidas se rechazan con el mensaje «Las cantidades de las partes deben ser enteros no negativos y el total debe estar entre 1 y 100.».
- **HU-03 (Inyectar piezas, CU-03, solo *Encargado de Despacho*):** en `/proyectos`, un proyecto en **"Aprobado"**, con partes definidas y cero piezas, muestra **un único botón** **«Inyectar piezas desde plano/archivo»**. El proyecto recién creado está **"Pendiente de aprobación"**: debe aprobarlo el *Supervisor de Proyectos* en `/aprobaciones` para que aparezca el botón; en **"Rechazado"** o **"Pendiente de aprobación"** la inyección se rechaza sin modificar datos (HU-03 CA4). Al pulsarlo se crean, en una sola carga, **exactamente las cantidades previstas** de cada parte (total 1–100), en estado **"Pendiente"** y sin torre; el proyecto pasa a **"En preparación"**, el botón desaparece y los reintentos se rechazan sin modificar datos. La pantalla muestra la cantidad prevista y las piezas creadas por parte. Cada pieza recibe un código con una letra de la A a la Z y un número del 1 al 25 (p. ej. `A3`, `I5`), elegidos al azar; el código completo no se repite dentro del proyecto —también lo refuerza `UNIQUE (proyecto_id, codigo)` en la migración 003—, pero proyectos distintos pueden compartir códigos. La inyección **no** ocurre al crear el proyecto.
- **HU-04 (Crear torre, CU-04, solo *Operario de Bodega*):** `/torres/nuevo`. Elija un **Proyecto** —mostrado como `cliente (codigo)`—; al seleccionarlo el selector de **Parte de la casa** se llena solo (mismo patrón de HU-06). Pulse **«Crear torre»**. La confirmación muestra el proyecto, la parte, el número correlativo del proyecto, el código generado `TOR-<codigo>-<numero>`, el estado **"Abierta"** y «sin piezas asignadas». Puede crear varias torres para la misma parte: la numeración sigue correlativa y las torres anteriores no se modifican. Si el proyecto está **"Pendiente de aprobación", "Aprobado" o "Rechazado"** sin piezas, el sistema rechaza con «primero deben inyectarse las piezas del proyecto desde el archivo» (HU-02 CA3); si la parte no pertenece al proyecto, rechaza con «La parte de la casa no pertenece al proyecto seleccionado.». El enlace aparece solo para el Operario.
- **HU-05 (Asignar pieza a torre con evidencia, CU-05, solo *Operario de Bodega*):** `/piezas/asignar`. Elija un **Proyecto**: se listan sus piezas «Pendiente» y **todas** sus torres, cada una con código, parte de la casa y estado. Seleccione una pieza, una torre y **una de las tres fotos de demostración**; no hay campo de texto ni subida real de archivos. Al asignar, la pieza queda «Listo» y la evidencia registra responsable, fecha/hora y vigencia; la confirmación muestra el código de la torre y enlaza a su consulta. Si la pieza ya está «Listo», el sistema pide **confirmar** el reemplazo; la evidencia anterior se conserva en el historial como no vigente. Rechazos: «se exige evidencia fotográfica» (sin foto), «la torre no corresponde a la parte de la pieza» (otra parte), «se sugiere registrar otra torre para la parte» (torre Cerrada), «una pieza enviada no puede reasignarse» (pieza «Enviado», preparada en BD desde las pruebas) y «la evidencia no pudo almacenarse» (fallo simulado con `EVIDENCIA_FORZAR_FALLO=1`). Cada torre del listado tiene «Consultar piezas» → `/torres/consultar/:id` (CA6), que muestra el código y el estado de las piezas asignadas.
- **HU-06 (Consultar piezas pendientes, CU-06, solo *Operario de Bodega*):** `/pendientes`. Elija un **Proyecto** —mostrado como `cliente (codigo)`—. En cuanto lo selecciona, **el selector de Parte de la casa se llena solo**, con las partes de ese proyecto que tienen piezas cargadas (CA4/CA5): no hace falta pulsar «Consultar» ni tocar la URL. Cambiar de Proyecto descarta la Parte antes elegida. Después elija una **Parte de la casa** y pulse «Consultar». Cada proyecto se identifica por su cliente y su código (CA3); si el proyecto está en estado **"Pendiente de aprobación" o "Rechazado"**, el selector queda vacío y se informa que no tiene partes con piezas cargadas (CA6). La pantalla muestra solo los códigos de piezas en estado **"Pendiente"** (sin torre asignada) de esa parte; excluye otras partes y otros estados. Si la parte elegida no tiene pendientes, muestra **«0 pendientes para <parte>»**. Si falta proyecto o parte, pide la selección y **no** muestra ese mensaje. El enlace aparece en el inicio solo para el Operario; `/proyectos` sigue siendo solo del Encargado.

> **Integración simulada:** el plano/archivo se sustituye por `GeneradorPlanoSimulado` (`src/integraciones/`), que recibe las partes guardadas por HU-02 y solo elige los códigos de las piezas; no hay carga de archivo, lectura de plantilla ni validación de formato. Para probar otra distribución de piezas, crea otro proyecto con otras cantidades previstas: cada inyección usa números aleatorios para los códigos.

> **Evidencia simulada (HU-05):** el `ServicioAlmacenamientoEvidencias` se sustituye por `ServicioAlmacenamientoEvidenciasSimulado` (`src/integraciones/`): tres fotos de demostración, elegibles con un clic y sin subida real. Para probar el rechazo CA4, defina `EVIDENCIA_FORZAR_FALLO=1` antes de iniciar la app (no es una cuarta opción visible).

## Correr las pruebas
```bash
npm test
```
Las pruebas usan una base SQLite temporal y cubren los escenarios definidos para:
- **HU-01:** acceso por rol, rechazo sin rol, rechazo por rol no autorizado sin modificar datos, y cambio de rol.
- **HU-02:** creación de proyecto con código único y partes con cantidades previstas (CA1), rechazo por código duplicado conservando el existente (CA2), proyecto "Pendiente de aprobación" con partes y sin piezas (CA3; el rechazo al crear torre se implementa en HU-04) y rechazo de cantidades inválidas (CA4).
- **HU-03:** inyección simulada con cantidades exactas por parte (CA1), total 1–100, formato y unicidad de códigos, repetibilidad forzada entre proyectos con generador fijo y rechazo de duplicados dentro de un proyecto, rechazo por rol no autorizado (HU-01 CA3), botón único, ocultación del botón y rechazo de reintentos sin modificar datos, y los dos escenarios de CA2 adaptados a la demo como **desviación documentada**.
- **HU-04:** creación de torre con `numero = 1`, `estado = "Abierta"`, cero piezas y código visible (CA1), rechazo por proyecto sin piezas con el mensaje de HU-02 CA3, segunda torre para la misma parte con numeración correlativa y torres anteriores conservadas (CA2), numeración independiente entre proyectos, rechazo de parte ajena al proyecto y rechazo por rol no autorizado sin revelar datos.
- **HU-12:** proyecto nuevo en «Pendiente de aprobación» (HU-02 CA1), aprobación por el Supervisor (CA1), rechazo por el Supervisor (CA2), decisiones rechazadas sobre proyectos «Aprobado» o «Rechazado» sin modificar datos (CA3) y rechazo de Operario, Encargado y petición sin rol en `/aprobaciones` y en las rutas POST directas (CA4).
- **HU-06:** identificación del proyecto por cliente y código (CA3), oferta de las partes del proyecto elegido con los cinco ejemplos del esquema (CA4), selector limitado a las partes que existen en ese proyecto (CA5), aviso de proyecto sin piezas en «Pendiente de aprobación» o «Rechazado» (CA6), listado filtrado por parte y estado (CA1), mensaje «0 pendientes» para una parte elegida (CA2), petición de selección cuando falta proyecto o parte, llenado automático del selector de Parte al elegir Proyecto, descarte de la Parte anterior al cambiar de Proyecto y rechazo por rol no autorizado sin revelar piezas.
- **HU-05:** listado de piezas «Pendiente» y de **todas** las torres con código, parte y estado, sin foto preseleccionada; asignación de una pieza pendiente con evidencia (CA1); rechazo sin evidencia (CA2), de otra parte (HU-04 CA3), de torre Cerrada (HU-04 CA4), de pieza «Enviado» (CA5) y por fallo del servicio (CA4); reasignación confirmada y no confirmada (CA3), con la evidencia anterior no vigente y sin tabla de guías; consulta de las piezas de una torre con código y estado (CA6) y rechazo por rol no autorizado. **65 pruebas en total** (49 del baseline + 16 añadidas para HU-12, HU-01 y el ajuste del ciclo).

## Estructura relevante
- `src/app.ts` — crea la app Express (sin escuchar)
- `src/server.ts` — arranque del servidor
- `src/db/` — conexión, migraciones (`migrations/`) y seed
- `src/dominio/` — lógica de dominio (`proyectos.ts`, HU-02/HU-12; `piezas.ts`, HU-03; `torres.ts`, HU-04; `asignaciones.ts`, HU-05; `pendientes.ts`, HU-06, solo lectura)
- `src/integraciones/` — interfaces y adaptadores simulados (`ServicioAutenticacionSimulado`, `GeneradorPlanoSimulado`, `ServicioAlmacenamientoEvidenciasSimulado`)
- `src/rutas/`, `src/vistas/`, `src/middleware/`, `src/acceso/` — rutas, vistas, autorización y acceso por rol (`torres.ts` con `torre-nuevo.ejs`/`torre-creada.ejs` para HU-04; `asignaciones.ts` con `asignacion-nueva.ejs`, `asignacion-confirmar.ejs`, `asignacion-creada.ejs` y `torre-consultar.ejs` para HU-05; `pendientes.ts` y `pendientes.ejs` para HU-06; `aprobaciones.ts` y `aprobaciones.ejs` para HU-12)
- `tests/` — pruebas automatizadas por escenario (`HU-01 · ...`, `HU-02 · ...`, `HU-03 · ...`, `HU-04 · ...`, `HU-05 · ...`, `HU-06 · ...`, `HU-12 · ...`)
- `openspec/` — cambios OpenSpec archivados (`openspec/changes/archive/`, uno por historia y por ajuste) y especificaciones vigentes (`openspec/specs/`)
