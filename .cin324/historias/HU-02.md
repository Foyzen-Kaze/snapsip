## Historia de usuario
> Como Encargado de Despacho, quiero registrar un nuevo proyecto asociado a un cliente, para iniciar el control de todas las piezas que se esperan producir para esa casa.

## Criterios de aceptación (fuente: `04-historias-usuario.md` y `07-criterios-aceptacion.md`)
- **CA1 — Creación de un proyecto con código único:** Dado que el encargado de despacho dispone del cliente, el código, el metraje y las cantidades de Piso, Muros exteriores, Muros interiores, Entrepiso y Techo, el código no pertenece a otro proyecto y las cantidades son válidas, cuando solicita crear el proyecto con esos datos, entonces el sistema registra el proyecto asociado al cliente, conserva el código y el metraje, establece su estado en "Pendiente de aprobación", crea las partes con cantidad positiva y su cantidad prevista, y deja el proyecto sin piezas.
- **CA2 — Rechazo de un código de proyecto duplicado:** Dado que existe un proyecto registrado con un determinado código, cuando el encargado de despacho solicita crear otro proyecto con ese mismo código, entonces el sistema rechaza la solicitud, comunica que el código está duplicado y conserva el proyecto existente sin modificaciones.
- **CA3 — Rechazo de la creación de una torre antes de inyectar las piezas:** Dado que un proyecto se encuentra en estado "Pendiente de aprobación", "Aprobado" o "Rechazado" con partes definidas y sin piezas, cuando el operario de bodega solicita crear una torre en ese proyecto, entonces el sistema rechaza la solicitud e informa que primero debe completarse la carga del plano o archivo de piezas.
- **CA4 — Validación de las cantidades de las partes:** Dado que una cantidad no es un entero no negativo o el total de las cinco cantidades está fuera de 1–100, cuando se solicita crear el proyecto, entonces el sistema rechaza la solicitud con el mensaje «Las cantidades de las partes deben ser enteros no negativos y el total debe estar entre 1 y 100.» y no registra el proyecto ni sus partes.

## Entidades del modelo de dominio involucradas
- **`Proyecto`** (`08-modelo-dominio.md` / `diagramas/modelo-de-dominio.puml`, fuente de verdad): atributos `codigo`, `cliente`, `metraje`, `estado` (valores documentados: *Pendiente de aprobación*, *Aprobado*, *Rechazado*, *En preparación*, *Proyecto completo*).
- Al crear el proyecto (CA1) queda asociado al cliente, con código y metraje conservados, en estado **"Pendiente de aprobación"**, con las **`ParteCasa` definidas** (una por cada una de las cinco con cantidad positiva, con su `cantidad_prevista`) y **cero `Pieza`**.
- HU-02 crea `ParteCasa` y gestiona sus cantidades previstas; **no** crea ni gestiona `Pieza`, `Torre`, `GuiaDespacho` ni `Evidencia` en este alcance.

## Cambios de estado relevantes
- HU-02 establece el estado inicial del proyecto en **"Pendiente de aprobación"** (CA1).
- HU-02 **no** realiza transiciones a *"En preparación"* (HU-03) ni a *"Proyecto completo"* (HU-08).
- La aprobación y el rechazo se rigen por EST-04 (HU-12); HU-02 solo fija el estado inicial *"Pendiente de aprobación"*.
- `Proyecto` sí tiene diagrama de estado propio: **EST-04** (`11-diagramas-estado.md:111-147`); los estados y transiciones se rigen por ese diagrama, HU/CA, modelo y trazabilidad.
- **Alcance de CA3:** CA3 expresa que, con proyecto en *"Pendiente de aprobación"*, la creación de una torre (CU-04/HU-04, actor Operario de Bodega) debe rechazarse. **HU-02 deja representable la condición** (proyecto en "Pendiente de aprobación", con partes definidas y sin piezas); la regla/mensaje de rechazo al intentar crear la torre se materializa en **HU-04** (fuera de alcance de HU-02), salvo corrección posterior acordada.

## Flujo de interacción esperado (reconstruido; sin DSS propio)
1. Un usuario con rol de demostración **Encargado de Despacho** accede a la función de **crear proyecto** (HU-01 ya implementada: acceso por selector de rol de demostración, sin credenciales reales; operaciones protegidas autorizadas por rol y rechazadas sin modificar datos si no corresponde).
2. Solicita registrar un proyecto indicando **cliente, código, metraje** (campos obligatorios) y las **cantidades de Piso, Muros exteriores, Muros interiores, Entrepiso y Techo**.
3. **Validación de unicidad (CA2) y de cantidades (CA4):** si ya existe un proyecto con ese **código**, se rechaza por duplicado; si alguna cantidad no es un entero no negativo o el total está fuera de 1–100, se rechaza con el mensaje acordado.
4. **Éxito (CA1):** si el código no existe y los datos son válidos, el sistema registra el proyecto asociado al cliente, conserva código y metraje, lo establece en estado **"Pendiente de aprobación"**, crea las partes con cantidad positiva y su cantidad prevista, y deja **cero piezas**.
5. El sistema presenta confirmación/resultado coherente con lo registrado.

## Dependencias y contexto
