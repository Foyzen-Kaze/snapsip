## Historia de usuario
> Como Encargado de Despacho, quiero registrar un nuevo proyecto asociado a un cliente, para iniciar el control de todas las piezas que se esperan producir para esa casa.

## Criterios de aceptación (fuente: `04-historias-usuario.md` y `07-criterios-aceptacion.md`)
- **CA1 — Creación de un proyecto con código único:** Dado que el encargado de despacho dispone del cliente, el código y el metraje del proyecto y el código no pertenece a otro proyecto, cuando solicita crear el proyecto con esos datos, entonces el sistema registra el proyecto asociado al cliente, conserva el código y el metraje indicados, establece su estado en "Sin piezas cargadas" y el proyecto queda sin partes de la casa ni piezas registradas.
- **CA2 — Rechazo de un código de proyecto duplicado:** Dado que existe un proyecto registrado con un determinado código, cuando el encargado de despacho solicita crear otro proyecto con ese mismo código, entonces el sistema rechaza la solicitud, comunica que el código está duplicado y conserva el proyecto existente sin modificaciones.
- **CA3 — Rechazo de la creación de una torre antes de inyectar las piezas:** Dado que un proyecto se encuentra en estado "Sin piezas cargadas", cuando el operario de bodega solicita crear una torre en ese proyecto, entonces el sistema rechaza la solicitud, comunica que primero deben inyectarse las piezas del proyecto desde el archivo y no crea la torre.

## Entidades del modelo de dominio involucradas
- **`Proyecto`** (`08-modelo-dominio.md` / `diagramas/modelo-de-dominio.puml`, fuente de verdad): atributos `codigo`, `cliente`, `metraje`, `estado` (valores documentados: *Sin piezas cargadas*, *En preparación*, *Proyecto completo*).
- Al crear el proyecto (CA1) queda asociado al cliente, con código y metraje conservados, en estado **"Sin piezas cargadas"** y **sin partes de la casa ni piezas registradas** (0 partes, 0 piezas).
- HU-02 **no** crea ni gestiona `ParteCasa`, `Pieza`, `Torre`, `GuiaDespacho` ni `Evidencia` en este alcance.

## Cambios de estado relevantes
- HU-02 establece el estado inicial del proyecto en **"Sin piezas cargadas"** (CA1).
- HU-02 **no** realiza transiciones a *"En preparación"* (HU-03) ni a *"Proyecto completo"* (HU-08).
- No existe diagrama de estado propio de `Proyecto`; los estados se rigen por lo documentado en HU/CA/modelo y trazabilidad.
- **Alcance de CA3:** CA3 expresa que, con proyecto en *"Sin piezas cargadas"*, la creación de una torre (CU-04/HU-04, actor Operario de Bodega) debe rechazarse. **HU-02 deja representable la condición** (proyecto en "Sin piezas cargadas", sin partes/piezas); la regla/mensaje de rechazo al intentar crear la torre se materializa en **HU-04** (fuera de alcance de HU-02), salvo corrección posterior acordada.

## Flujo de interacción esperado (reconstruido; sin DSS propio)
1. Un usuario con rol de demostración **Encargado de Despacho** accede a la función de **crear proyecto** (HU-01 ya implementada: acceso por selector de rol de demostración, sin credenciales reales; operaciones protegidas autorizadas por rol y rechazadas sin modificar datos si no corresponde).
2. Solicita registrar un proyecto indicando **cliente, código y metraje** (campos obligatorios).
3. **Validación de unicidad (CA2):** si ya existe un proyecto con ese **código**, el sistema rechaza la solicitud, comunica que el código está duplicado y conserva el proyecto existente sin modificaciones.
4. **Éxito (CA1):** si el código no existe y los datos requeridos son válidos, el sistema registra el proyecto asociado al cliente, conserva código y metraje, lo establece en estado **"Sin piezas cargadas"** y queda sin partes de la casa ni piezas registradas.
5. El sistema presenta confirmación/resultado coherente con lo registrado.

## Dependencias y contexto
- **HU-01 (hecha):** provee el contexto de acceso por rol de demostración. La operación de crear proyecto debe estar restringida al rol **Encargado de Despacho**.
