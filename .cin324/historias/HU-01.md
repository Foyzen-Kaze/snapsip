## Historia
Como Operario de Bodega, Encargado de Despacho o Supervisor de Proyectos, quiero autenticarme con mis credenciales, para acceder únicamente a los proyectos y funciones que corresponden a mi rol.

## Flujo de interacción
Flujo de referencia documentado (DSS-03, HU-01 CA1–CA3, RP-01/RP-16), adaptado a la regla del taller (ver Decisiones/Supuestos):

1. El **usuario** accede a la aplicación y selecciona/establece su **rol de demostración**: *Operario de Bodega*, *Encargado de Despacho* o *Supervisor de Proyectos* (mecanismo de acceso de demostración, sin credenciales reales).
2. **SnapSip** establece el contexto de acceso del usuario con el rol seleccionado y habilita únicamente las funciones/proyectos autorizados para ese rol.
3. **[Acceso concedido según rol — adaptación de CA1]:** el sistema muestra/concede acceso a las funciones correspondientes al rol seleccionado.
4. **[Operación no autorizada por rol — CA3]:** dado un usuario con rol que no autoriza una operación protegida, cuando solicita esa operación, el sistema rechaza la solicitud y conserva los datos sin modificaciones.

**Variantes:**
- Cambio de rol de demostración: el usuario puede cambiar el rol seleccionado para simular otro perfil (el sistema actualiza las funciones habilitadas según el nuevo rol).
- **CA2 (credenciales inválidas)** del Gherkin original no se representa literalmente en la Opción 2 (no hay ingreso de contraseña); ver Decisiones/Supuestos.

## Escenarios Gherkin (texto íntegro)
```gherkin
Característica: Autenticación de usuarios

  # CA1
  Escenario: Acceso con credenciales válidas
    Dado que un usuario posee credenciales registradas y un rol asignado
    Cuando solicita autenticarse con su identificador y su contraseña válidos
    Entonces el sistema concede el acceso
    Y habilita únicamente los proyectos y funciones autorizados para su rol

  # CA2
  Escenario: Rechazo de credenciales inválidas
    Dado que un usuario posee credenciales registradas
    Cuando solicita autenticarse con su identificador y una contraseña incorrecta
    Entonces el sistema rechaza la solicitud
    Y comunica que las credenciales son inválidas
    Y no concede acceso a las funciones protegidas

  # CA3
  Escenario: Rechazo de una operación no autorizada para el rol
    Dado que un usuario está autenticado
    Y su rol no autoriza una determinada operación protegida
    Cuando solicita realizar esa operación
    Entonces el sistema rechaza la solicitud
    Y conserva los datos sin modificaciones
```

## Supuestos
- **Mecanismo de acceso (Opción 2):** no habrá login con identificador/contraseña ni verificación real/administrada de credenciales. El acceso se realiza mediante **selector de rol de demostración** (*Operario de Bodega* / *Encargado de Despacho* / *Supervisor de Proyectos*). **CA1** se verifica como “al seleccionar/establecer un rol de demo, el sistema habilita únicamente las funciones de ese rol”. **CA2** (credenciales inválidas) **no es aplicable literalmente** bajo Opción 2 y se considera fuera del alcance de esta implementación de demo (desviación documentada respecto al Gherkin original). **CA3** se mantiene plenamente verificable.
- **Servicio de autenticación (DSS-03/CU-01):** documentado como sistema externo; bajo Opción 2 su participación no es necesaria para el flujo principal. Se registrará como simulado/omitido en la demo según convenga a la implementación, sin autenticación real.
- **Datos de acceso de demo:** se podrán usar roles/identidades de demostración precargados o seleccionables en la interfaz (p.ej. datos seed en SQLite o configuración simple) como soporte, sin modelarlos como entidades del dominio de SnapSip.

- Implementación de requisitos no funcionales (RP-13, RP-14, RP-15a, RP-15b) más allá de su contexto.
