## Historia de usuario
> Como Supervisor de Proyectos, quiero aprobar o rechazar un proyecto que se encuentre en estado "Pendiente de aprobación", para controlar qué proyectos están autorizados a pasar a la carga de piezas.

## Criterios de aceptación y Gherkin íntegro
Fuente: `07-criterios-aceptacion.md:562-593`. Se reproduce sin cambios.

```gherkin
Característica: Aprobar o rechazar proyecto

  # CA1
  Escenario: Aprobación de un proyecto pendiente
    Dado que un proyecto se encuentra en estado "Pendiente de aprobación"
    Cuando el supervisor de proyecto solicita aprobar el proyecto
    Entonces el sistema cambia el proyecto a estado "Aprobado"
    Y habilita el proyecto para la inyección de piezas

  # CA2
  Escenario: Rechazo de un proyecto pendiente
    Dado que un proyecto se encuentra en estado "Pendiente de aprobación"
    Cuando el supervisor de proyecto solicita rechazar el proyecto
    Entonces el sistema cambia el proyecto a estado "Rechazado"
    Y no permite inyectar piezas en el proyecto

  # CA3
  Escenario: Rechazo de aprobación o rechazo sobre un proyecto que no está pendiente
    Dado que un proyecto se encuentra en estado "Aprobado", "Rechazado" o "En preparación"
    Cuando el supervisor de proyecto solicita aprobar o rechazar el proyecto
    Entonces el sistema rechaza la solicitud
    Y mantiene el estado actual del proyecto sin modificaciones

  # CA4
  Escenario: Rechazo de aprobación o rechazo por un rol no autorizado
    Dado que un proyecto se encuentra en estado "Pendiente de aprobación"
    Y el usuario autenticado posee un rol distinto a Supervisor de Proyectos
    Cuando solicita aprobar o rechazar el proyecto
    Entonces el sistema rechaza la solicitud
    Y mantiene el proyecto en estado "Pendiente de aprobación"
```

**Lectura de CA3/CA4:** en ambos casos el sistema solo rechaza la solicitud; **no modifica datos** (conserva el `estado` y cualquier otra información del proyecto). CA3 enumera «Aprobado», «Rechazado» y «En preparación»; el mismo criterio se aplica a «Proyecto completo» por ser un estado posterior del mismo ciclo (EST-04).

## Flujo de interacción esperado (reconstruido; sin DSS propio)
1. El usuario selecciona el rol de demostración **Supervisor de Proyectos** (HU-01). Ese rol se agrega al selector (`src/acceso/roles.ts`) y a CU-01/HU-01 en este ciclo, junto con la función «Aprobar o rechazar proyecto (HU-12)».
2. El Supervisor abre su **pantalla propia `/aprobaciones`**, separada de `/proyectos` (que sigue restringida al Encargado de Despacho por HU-02/HU-06). La pantalla lista los proyectos con su cliente, código y estado, y ofrece **Aprobar** y **Rechazar** solo cuando el estado es «Pendiente de aprobación».
3. **CA1 — Aprobar:** si el Supervisor solicita aprobar un proyecto pendiente, el sistema cambia el estado a **«Aprobado»**. Ese estado habilita el botón de inyección de HU-03 para el Encargado de Despacho.
4. **CA2 — Rechazar:** si solicita rechazar un proyecto pendiente, el sistema cambia el estado a **«Rechazado»**. Desde ese estado no se pueden inyectar piezas ni crear torres.
5. **CA3 — Estado no pendiente:** si el proyecto está «Aprobado», «Rechazado», «En preparación» o «Proyecto completo», la solicitud se rechaza sin modificar el proyecto; no se ofrecen los botones para esos casos.
6. **CA4 — Rol no autorizado:** si la solicitud proviene de otro rol (incluso directamente al servidor), se rechaza sin modificar datos (HU-01 CA3, RP-16).
7. La autenticación sigue siendo simulada por selector de rol; no hay credenciales reales ni servicio externo invocado en el flujo principal (Opción 2 de HU-01).
